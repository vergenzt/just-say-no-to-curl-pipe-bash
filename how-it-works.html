How the server knows
you're piping to bash

The claim that "a server can serve you something different when you curl | bash" sounds like paranoia. It's a documented technique. Here's the mechanism.

00The intuition

When you save a file, your computer reads the whole response as fast as the network allows. When you pipe into bash, bash starts executing the script while it's still downloading — and that changes the timing of how fast your machine pulls bytes off the wire. The server can watch that timing.

The difference is observable from the server's side because of how pipes and TCP flow control work. Let's walk through it.

01The timing side-channel

What happens when you save to a file

curl https://… -o install.sh (or piping into cat, or a browser download) reads the response body continuously and dumps it to disk. Nothing inspects the bytes; nothing pauses. From the server's point of view, the client drains the connection at line speed and goes quiet only when it's done.

What happens when you pipe into bash

curl … | bash connects curl's stdout to bash's stdin through an OS pipe. Bash doesn't wait for end-of-file; it reads and executes commands as soon as it has a complete line. If one of those early commands blocks — say it runs sleep 5, or waits on the network, or just does real work — then bash stops reading from the pipe while it's busy.

The pipe between curl and bash has a fixed buffer (on Linux, classically 64 KiB). Once bash stops draining it and the buffer fills, curl's write() blocks. Curl then stops reading from the TCP socket; the kernel's receive buffer fills; TCP flow control kicks in and the receive window shrinks to zero; and the server's send() blocks too. The stall propagates all the way back to the server.

The tell
The server, sending the script in chunks, simply measures how long it takes for the client to accept the next chunk. A continuous drain looks like a file download. A pause at the exact point where an early command would have executed is the fingerprint of a live shell on the other end.

Making the pause reliable

The original proof-of-concept makes this deterministic. The server sends a first block that is padded — typically with a long bash comment — so it's large enough to fill the pipe and socket buffers, followed by a command that deliberately blocks (e.g. a sleep). Then the server tries to send the next block and times how long that send() takes to complete:

server-side logic (pseudocode)
# 1. Send a block big enough to fill the ~64 KiB pipe + socket buffers,
#    ending in a command that blocks for a beat.
send(padding_comment + "sleep 0.4\n")

# 2. Time how long it takes the client to accept the *next* byte.
t0 = now()
send(next_chunk)            # blocks if the client stopped reading
elapsed = now() - t0

if elapsed > threshold:
    serve_malicious_payload()   # a shell is executing us right now
else:
    serve_benign_payload()      # probably a download / browser / curl -o

If the client is bash, it executed the sleep, stopped reading, and the server's next send() hangs for ~0.4s — a giant, unambiguous signal. If the client is saving to a file, there's no pause, and the server happily serves the clean version. The reviewer who opened the URL in a browser, the security team that ran curl -o, the mirror that cached it — all of them see innocent code. Only the shells get the payload.

02The 1% attack

Detection is only half of it. The server also controls how often it misbehaves — and that's what makes this genuinely scary.

A response doesn't have to be the same twice. A malicious endpoint can:

  • Serve the real, working installer to everyone — so the software installs fine and nobody's suspicious.
  • Add the malicious payload only when it detects a live shell (per above), so anyone inspecting via download or browser sees nothing.
  • Do it to only a small fraction of piped requests — 1%, 0.1% — low enough that it rarely shows up in bug reports, and any single victim looks like a fluke.
  • Key off IP, geography, time, or User-Agent to target specific victims and stay dark for researchers and CI.
Why this beats "just read it once"
Reproducing the attack requires hitting the exact conditions the server is watching for — a real shell, the right slice of the dice, maybe the right IP — at the right moment. The clean version you inspected is not evidence about the version that ran. And because nothing was saved, there's no artifact to compare against afterward.

Compare this to a package registry, where a published version is an immutable, content-addressed artifact: everyone who installs foo@1.2.3 gets the same bytes, those bytes can be re-fetched and audited later, and if they turn out to be malicious the registry can yank them. A live HTTP endpoint offers none of that by construction.

03Defending yourself

Every defense here works by removing the live shell from the download, so the server can't distinguish you from an ordinary file fetch — and by keeping the bytes, so you have something to inspect and compare.

the safe ritual 
$ curl -fsSL https://example.com/install.sh -o install.sh
$ sha256sum install.sh    # compare to a published checksum
$ less install.sh         # read it
$ sh install.sh           # run the exact bytes you inspected
  • Download, then run a file. The server sees a plain download with no telltale pause.
  • Keep the artifact. You can re-read it, diff it, and prove what you ran.
  • Verify a checksum when the project publishes one — tampering becomes obvious.
  • Prefer a package manager with immutable, signed, mirrored artifacts whenever possible.
