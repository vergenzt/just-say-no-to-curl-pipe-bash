Just Say No to
curl | bash

You wouldn't run a script you've never read, from a server you don't control, that can change its mind every time you ask. So why pipe it straight into your shell?

~ — this is your shell on curl | bash 
$ curl -fsSL https://totally-legit.example/install.sh | bash
# ...and now? Anything. You'll never know what ran.
[ now executing 4,000 lines you never saw ]
[ nothing was saved. nothing was logged. good luck. ]
Why it's a bad idea I'm a user / distributor How the attack works

curl … | bash hands a remote server a blank check to run arbitrary code on your machine — without ever showing you the code, without keeping a copy, and without any guarantee the next person (or the next request) gets the same thing.

It's not that running install scripts is inherently evil. It's that this particular ritual strips away every safeguard that makes "running code from the internet" merely risky instead of reckless: inspection, a paper trail, reproducibility, and a way to pull the plug when something goes wrong.

The uncomfortable part
A server can tell whether you're piping its response into a shell, and serve you something different when you are — even just a small, hard-to-catch percentage of the time. Here's how that works →

Why it's a bad idea

🕵️

1. Untraceable & unauditable

The script is executed straight off the wire and then it's gone. No file on disk, nothing in your shell history but curl | bash. After the fact you have no way to know what actually ran on your computer — you can't diff it, review it, or even prove what it did.

🎭

2. The server knows you're piping

A web server can detect that its response is being fed directly into a shell (versus saved or viewed) and serve different content accordingly. The script you'd see if you opened the URL in a browser need not be the script that runs in your shell. (Yes, really.)

🎲

3. Every request is a fresh roll

Nothing forces a server to send the same bytes twice. A malicious endpoint can install the real software and slip in something extra just 1% of the time, only when piped to bash — low enough to dodge reports, invisible to everyone who checked.

Pick your lane

Two kinds of people can stop this. Which one are you?

// for the person typing it

I run install commands

You've seen a README that says curl … | bash and you're about to paste it. Don't — at least not like that.

Do this instead:

  • Download first, then read, then run. Split the pipe in two.
  • Prefer a real package manager when one exists (see below).
  • If you must use a script, save it and at least skim it for surprises.
the two-step 
$ curl -fsSL https://example.com/install.sh -o install.sh
$ less install.sh   # actually read it
$ sh install.sh      # now you know what ran

Saving the file also defeats reasons 2 & 3: a server can't tell curl -o from a browser, and you keep evidence of exactly what you received.

// for the person publishing it

I distribute software

Your README says curl … | bash because it's one line and it "just works." It also trains your users to do the most dangerous thing on the internet.

Do this instead:

  • Ship to real package managers (apt, dnf, Homebrew, npm, PyPI, cargo…).
  • Publish versioned, checksummed, signed release artifacts.
  • If you offer a script, tell people to download & inspect it — and pin it to a tagged, immutable URL.
  • Document the checksum so a tampered download is obvious.
The kindest thing you can do
is make the safe path the easy path. Every curl | bash in a README is a habit your users will carry to the next, less trustworthy README.

"But package managers run arbitrary code too!"

True — and it's the most common defense of curl | bash. It's also a false equivalence. "Arbitrary code" isn't one risk level; the distribution channel around the code is what matters.

A package registry is a moderated, accountable system: artifacts are uploaded under an identity, pinned to immutable versions, fingerprinted with checksums, often signed, and — crucially — can be yanked by the registry operator when they turn out to be malicious. An arbitrary web endpoint is, by design, none of those things. It answers only to whoever owns the domain, and the only way to "take it down" is to convince a hosting provider or law enforcement — which is slow, jurisdiction-dependent, and reactive.

Property curl | bash Package registry
(npm, PyPI, apt, Homebrew…)
You can read the code before it runs No (by design) Usually (source / cached artifact)
The same version is identical for everyone No guarantee Yes (immutable, pinned versions)
Integrity check / checksum / signature Rarely Standard (hashes, lockfiles, signing)
Audit trail (who published, when) None visible to you Yes (account + publish history)
Can be centrally revoked / yanked Only via the host or law enforcement Yes (registry can pull it)
Can serve different code per request / per client Yes — trivially No (cached, mirrored, content-addressed)
Honest footnote
Specifics vary by ecosystem — some registries sign by default, some rely on lockfile hashes, some have stronger moderation than others, and none are perfect (typosquatting and account takeovers are real). The point isn't that registries are flawless. It's that they give you handles — inspection, immutability, identity, revocation — that a raw curl | bash endpoint deliberately doesn't.

Maintainer's note: claims about per-registry log retention and revocation policies are worth verifying against each registry's current documentation before citing them in a specific argument.

Objections, fielded

"If I don't trust the software, why would I install it at all?"

Trust isn't binary. You can trust a project's intentions and still want defenses against a compromised server, a hijacked domain, a man-in-the-middle, or a malicious mirror. Reading the script and keeping a copy protects you even when the author is perfectly trustworthy but their infrastructure isn't.

"It's HTTPS, so it's safe, right?"

HTTPS protects the bytes in transit. It says nothing about whether the server itself is honest, compromised, or serving you a different payload than it served the reviewer down the hall. TLS authenticates the pipe, not the contents.

"I read the script in my browser first. Good enough?"

Not quite. The bytes your browser fetched and the bytes your shell executes are two separate requests to a server that's free to answer them differently — including based on whether the second one looks like it's being piped into bash. See how a server can tell → Download the exact file once and run that file.

"Splitting it into two commands is just security theater."

It's modest, but it's real. Saving to a file means the server sees an ordinary download it can't distinguish from a browser, you get an artifact you can inspect and re-inspect, and you can compare it to a published checksum. That defeats two of the three problems on this page outright.

"Everyone does it. The big projects do it."

They do, and that's exactly why it's worth pushing back — popularity is what normalizes the habit. Plenty of those same projects also ship to real package managers and publish signed releases. Use those.

Take the D.A.R.E. pledge

Don't Auto-Run Echoed-from-the-internet scripts.

  1. I will download before I run, and read what I downloaded.
  2. I will reach for a real package manager when one exists.
  3. If I publish software, I will stop asking strangers to pipe my server into their shell.
  4. I will remember that HTTPS protects the pipe, not the payload.
  5. I will be the friend who says, gently, "hey… maybe don't curl | bash that."
